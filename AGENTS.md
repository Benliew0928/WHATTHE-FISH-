# Instructions for every task in this repository

## Localization for every task

- Every new or changed player-visible text/string must ship in all three supported languages: **English, Simplified Chinese (简体中文), and Bahasa Melayu**. Update the shared localization catalog and any text embedded in artwork in the same task; do not leave English-only additions or untranslated fallback labels.
- Preserve placeholders, user-entered names/chat, room codes and protocol identifiers. Translate game-authored wording, not player content or internal identifiers.
- Check all three languages in the affected menus and gameplay: text must remain inside its intended bounds without overlapping other labels/icons. Preserve the English version's button shape, icon, colors and typography treatment. Run the localization checks and visually review affected layouts before delivery.

## APK delivery

- The self-contained hackathon APK must be **strictly below 1,000,000,000 bytes** (1 decimal GB, not 1 GiB; updated by the user on 17 October 2026). Never call an oversized build submission-ready.
- The former 75,000,000-byte development target and 100 MB cap are retired. Do not constrain requested features to those old budgets. The current measured baseline is in `Docs/BUILD-SIZE.md`.
- Read `Docs/BUILD-SIZE.md` and, when changing assets/rendering/build settings, `Docs/APK-SIZE-AUDIT.md`. Record the existing APK bytes before changes. Measure the resulting APK itself; source-folder sizes and uncompressed Unity reports are different measurements.
- For changes that can affect the delivered game, run `Tools/Build/Build.ps1 -Target AndroidSubmission` after the appropriate feature checks. It builds and enforces the hard limit. Inspect `Builds/SizeAudit/latest/` for the largest contributors and unexpected growth. Report before/after bytes and remaining headroom, and update the size documentation after a new measured release. If the build cannot run, state that size is unverified; do not present an older APK as validation of new code. Documentation/housekeeping-only changes do not require rebuilding Unity.
- Preserve sensible mobile performance and asset reuse without imposing the retired size targets.
- Preserve the intended visual quality: cabin interiors, close props, island silhouettes, animation and travel should remain attractive. Keep editable high-quality masters; derive mobile delivery assets. Check affected close/distant views and gameplay after lossy changes. Never claim phone quality/FPS from a Windows preview alone.
- Preserve the current world model: four islands, one active game per host room, everyone travels together. Keep cabin, cables, towers and stations modular.

## Windows testing player delivery

- After each delivered gameplay or asset change, update the complete validated Windows player in **`Builds/WindowsFinal/`**. Keep `WhatTheFish.exe`, `WhatTheFish_Data/`, runtime DLLs, supporting folders and launchers together; replacing only the executable does not update a Unity game.
- If validation uses an isolated checkout or task-specific player folder, promote that complete tested player to `Builds/WindowsFinal/` before handoff. Archive the reviewed superseded delivery with the repository's archive tool, preserve the task's validation evidence, and do not replace a newer concurrent delivery with an older snapshot. After verifying every promoted file, remove the redundant candidate created by this task under the generated-output rules below; do not archive another identical player copy.
- Update `Builds/WindowsFinal/LATEST-BUILD.txt` with build time, included changes, verification evidence and any source-snapshot limits. Keep all build output ignored. Documentation-only tasks do not require a new player.

## Portable paths are required in commits

- Never commit machine-specific absolute filesystem paths in code, scripts, configuration, documentation, generated records or active asset references. This includes personal drive locations, user/home directories, network shares and local file URLs. A teammate must be able to clone the project into a different directory without editing committed paths.
- Use document-relative links in Markdown/HTML, repository-relative paths in manifests with a documented base, and script/runtime project-root resolution based on the script or project location. Do not derive the default project root from the caller's working directory.
- Keep tool-installation paths and external locations in documented environment variables or explicit command-line overrides. Resolve standard system locations through the platform environment. Each developer sets their actual local values outside Git; do not commit those values, user settings or secrets.
- Save Blender dependencies relative to their master and export active FBX texture references relative to the FBX. Update generators so regeneration preserves portability. Check that targets exist in the publishable clone, preserve asset content, and refresh verified integrity hashes when path-only changes alter source bytes.
- Before committing, run `Tools/Build/Check-TaskReady.ps1` (which calls `Check-PortablePaths.ps1` for publishable working text). After staging the intended files, run `Tools/Build/Check-PortablePaths.ps1 -Staged` to inspect the exact indexed text blobs. Fix every finding and verify new links and defaults from a different checkout path, including paths with spaces and an unrelated working directory.
- Text scanning does not validate opaque binary payloads. When creating or changing art, inspect dependencies with format-aware Blender/FBX tooling and run the applicable asset/build checks. Never blind-replace bytes in binary assets.
- Nonfunctional exporter/native-source provenance, embedded preview metadata and saved Blender UI history may retain historical machine paths only when format-aware inspection proves they are not active dependencies and the exception is recorded in the task report. The existing retained art metadata is such an exception; absolute active image/library paths or FBX `RelativeFilename` values are never exempt.
- These instructions and readiness checks are required workflow steps, not an automatically installed Git hook or proof that no binary string exists. Preserve unrelated work and follow the publishing authorization rule below.

## Repository hygiene after every task

- Leave the workspace ready for the user to run `git add .`, commit and push themselves. **Do not stage, commit, push, reset, or rewrite history unless explicitly requested.** Preserve unrelated changes already in the workspace.
- Keep active source, Unity assets and their `.meta` files, package locks, generators, fixtures, current documentation and useful approved design references in Git. Generated delivery assets used by the build also belong in Git unless the normal fresh-clone build reliably regenerates them.
- Put temporary build output, raw logs, captures and audit data under ignored `Builds/`. Keep the current APK/player and current validation evidence there. Never place archives or experiments under `Game/Assets/Resources` or `StreamingAssets`.
- Move confirmed obsolete authored assets, superseded deliveries, non-regenerable drafts and recovery backups to **`Legacy/<dated-task-batch>/<original-relative-path>`**, outside the Unity project. `Legacy/` stays ignored. Use `Tools/Build/Archive-LocalArtifacts.ps1` with an explicit list of reviewed paths. It records sizes, SHA-256 hashes and recovery paths before moving. Do not overwrite earlier archives. Disposable generated output created by the current task follows the exception below instead of accumulating in Legacy.
- Prove a game asset is unused before archiving it: check scene/prefab/material references, string-based runtime loads, editor/build generators and source provenance. Absence from a packed-assets report alone is insufficient. Move Unity assets with their `.meta` files and fix active references. Keep Unity caches and installed dependencies in place; ignoring them is sufficient.
- Update `.gitignore` for newly introduced local-only output. Ignore rules do not remove files already tracked. Check the actual candidate set; do not blanket-ignore active art or remove authoring masters just to make Git smaller. Existing Git history is not rewritten by cleanup.
- Use Git LFS for the binary types in `.gitattributes`. A clean clone with LFS must retain enough files to build and edit the game. Keep secrets/signing keys outside commits.

## Prevent generated-output growth

- Before generating a large output, check whether the current source-matched player, packaged content or previous successful check already covers the unchanged behavior. Reuse valid results and run checks appropriate to the actual change. Keep the required AndroidSubmission and Windows delivery checks for game changes; documentation-only tasks must not build Unity players or copy the project.
- Do not create a full repository snapshot, ZIP or portable mirror for routine tasks. Use a source hash manifest and the necessary diff/source files to record uncommitted work. Test path portability with a minimal fixture. When a real isolated build is necessary for concurrent work or a reproducible failure, record the reason, copy only required publishable sources/assets, and exclude `.git`, `Builds`, `Legacy`, Unity caches, installed dependencies and other generated output. Never seed it by recursively copying the entire workspace or another validation snapshot. Let isolated tools restore only the dependencies they need.
- Use one candidate player location per feature/task and reuse it between iterations when no running process or required rollback depends on it. Do not create a complete player or project copy for every retry, screen size or language. Prefer the existing scripts-only build path for code-only changes only when the full build's serialized layouts/assets and packaged payload remain compatible.
- Keep the pre-task delivery as the designated rollback for each affected platform. Do not create an additional recovery archive for every intermediate build from the same task; after the final delivery passes, treat reproducible task-created intermediate players/APKs as disposable generated output. Existing archives remain subject to their preservation rules.
- Reuse compatible content caches across tests using their actual platform/catalog hash. When adding or changing runners, support a shared cache path instead of copying the same bundles into each run/feature folder. Separate caches only for genuine cold-cache, corruption or version-isolation tests; keep the main Unity cache and installed dependencies in place.
- Retain compact final evidence: assertions/results, build/source hashes, relevant failure diagnosis, and representative screenshots or an approved review video covering the required languages/layouts. Avoid retaining full frame sequences, repeated audit copies, duplicate source trees or complete players as evidence when those compact records suffice. Do not discard unique evidence still needed to assess a failure or validate the delivered game.
- At task completion, remove only reviewed, reproducible temporary output **created by this task** under ignored `Builds/`: completed minimal fixtures/isolated copies (including caches/dependencies generated solely inside those disposable copies), intermediate generated captures, isolated test-only content caches and candidate players verified identical to the promoted delivery. Record the exact paths and reason in a small cleanup result before removal. Resolve targets from the repository root, verify containment and reject links/junctions; check that no running process or active build/test depends on them. This narrow cleanup is authorized without another confirmation. Use the managed-worktree archive tool for managed Git worktrees; do not delete their directories directly.
- This exception does not authorize deleting pre-existing files/archives, the current delivery, the designated rollback, current validation evidence, authored assets, masters, Git/LFS data, main Unity caches or shared/pre-existing installed dependencies. Follow their existing preservation rules. `Legacy` is recovery storage, not a disposal bin: moving files there or adding ignore rules does not free SSD space. Report remaining generated output and any intentionally retained large copy before handoff; never call archival a disk-space saving.

## Before handing the task back

1. Run checks appropriate to the change and fix actionable failures. The AndroidSubmission build handles the APK limit automatically.
2. Apply the generated-output retention/cleanup rules; archive non-regenerable obsolete material, keep compact current evidence and update affected documentation/links.
3. Run `Tools/Build/Check-TaskReady.ps1` (add `-RequireApk` when delivering an Android build). Review `git diff --stat` and `git status --short`. The script is read-only; it does not certify APK freshness or replace functional/device testing.
4. State what changed, verification and any unresolved limits. Detailed size reporting is optional. Mention the archive batch if files moved. Leave all Git publishing actions to the user.
